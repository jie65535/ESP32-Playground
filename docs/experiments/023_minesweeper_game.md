# 实验 023：PGOS 扫雷

> 日期：2026-07-23
> 状态：已加入 Xbox 双击 A/X 的可证明局面辅助；主机测试、目标固件构建和离线预览均已完成。用户已执行一次上传，但该上传与最终本地构建并发且镜像尺寸不同，待单独重新烧录后手工体验验收

## 目标

在 320×240 PGOS 上实现完整的经典扫雷，而不是只提供简化演示或互斥的“休闲/硬核”模式：
标准初级/中级/专家和自定义棋盘使用同一套规则，首击安全，默认每一盘都能在不猜测的前提下完成；同时提供手柄操作、成绩资料和有节奏的视觉/声音反馈。

## 规则引擎与生成

- `MinesweeperEngine` 是不依赖 Arduino、LVGL 或 NVS 的纯 C++ 模块。标准配置为 9×9/10、16×16/40、30×16/99；自定义范围为 8–30 列、8–16 行，雷数上限为 24% 且始终保留首击九宫格。
- 首击后才开始生成。候选盘会先建立相邻数字，再由 `MinesweeperSolver` 从首击洪泛区出发执行局部数字规则、全局剩余雷规则和集合包含推理；只有全部安全格都能被证明时才接受。求解器不会通过隐藏地雷信息选择下一步，也没有概率兜底。
- App 每个 tick 只验证一个候选盘。标准盘主机基准为初级平均 1.2 / 最差 2 个候选、中级 1.7 / 2、专家 11.9 / 46；这样生成期显示 `LOGIC CHECK`，而非长时间阻塞 UI。
- 引擎覆盖翻开、零区洪泛、插旗、已翻数字的 chord、错误 chord 的引爆和胜负。首击即胜也会进入正常结算路径；结算只提供新棋盘或返回难度，避免已知雷位的复盘局污染正式成绩。
- `MinesweeperDeduction` 接收的只有当前棋盘尺寸、总雷数、已翻数字和格子可见状态；双击辅助在同一份可见快照中完成局部数字、全局剩余雷和集合包含推理，再固定候选集执行一次。手动旗帜只是不可自动翻开的玩家标记，并不直接成为推理事实；因此一致但错误的旗帜不能把“自动安全展开”导向地雷，旗帜与数字/总数矛盾时辅助直接不动作。实现不读取隐藏雷图来选择候选。

## 前台体验

- `MinesweeperApp` 使用状态栏下方的 320×218 单一 LVGL 自绘面，不创建每格的 LVGL 子对象。棋盘按密度使用 18px、11px 或 10px 格；凸起/下沉砖、5×7 数字、七段雷数/计时器和高对比光标保持经典像素质感。常规光标移动只失效旧格与新格，绘制回调再按 LVGL 的 clip 区域跳过所有不相交格子；翻格波纹和结算演出仍保留短暂的全盘动画。
- 标题提供四档难度和正式 `RECORDS` 入口；自定义页可独立修改宽、高、雷数。A 单击翻格或 chord，双击 A 自动展开本次可证明安全的固定候选；X 单击插旗，双击 X 会先撤销第一下在原格的临时旗帜变化，再自动给可证明为雷的格子插旗。第一下始终立即执行，没有等待双击窗口。Start 暂停；D-pad 作为满幅八方向输入，左摇杆保留死区后的实际 X/Y 幅度，并以独立积累器按满幅 14 格/秒比例推进。因而斜向摇杆会按实际角度产生对应比例的阶梯路径，而非固定 45 度。A/X 正常使用 BLE `ButtonDown` 事件，App 同时对当前手柄状态做一次去重后的上升沿兜底，避免队列边界造成短按漏接。专家 10px 格使用整格高对比脉冲选框和轻微填充，不再依赖几段难辨的黄角。USB/TCP 提供 `page minesweeper`、`page mines`、`flag`、`pause`；控制台快捷键为 `M`、`F`、`Z`。
- 新开区域按曼哈顿距离波纹展开，插旗生长；失败按空间波纹展示地雷和错误旗帜，正确旗帜保留；胜利自动插旗。结算面板在演出完成后才响应“再来一局”或“难度”，系统 Back/Home 保持全局语义。
- 计时从已接受的首击棋盘开始，Start 暂停期间不累计。A/X/Start 在屏幕息灭后的第一次输入只唤醒背光，不会误改游戏状态。

## 持久化与反馈

- `MinesweeperProfileService` 使用 `pgos_mines`、schema 1 保存三种标准难度各自升序 Top 5、局数、胜局、当前/最佳连胜，以及自定义胜局/总局和最后一套设置；未变化的设置不写 Flash。
- 翻格、插旗、胜负使用可变频游戏音；游戏音会抢占普通 Shell 反馈，避免结果旋律继承旧提示音的尾音。双击辅助成功时使用独立短音、短震动和 RGB 短闪，并在顶部状态区显示 `AUTO FLAG` / `SAFE OPEN` 的计数；无确定动作只显示 `NO CERTAIN MOVE`。该反馈只失效顶部小区域，不触发专家盘整屏重绘。手柄连接时插旗和胜负请求分级震动；RGB 开启时胜利短闪绿色、失败短闪红色，结束后恢复用户的原灯效并不写入灯光配置。

## 真机反馈与修正

2026-07-23 用户首次烧录后发现两项首屏问题：难度副标题中的 `×`、`·` 由只含拉丁字形的 LVGL 小字体绘制，真机显示为方块；单次 D-pad 离散事件与同轮连续状态采样使用了前后颠倒的毫秒时间戳，无符号减法回绕后导致“初级”一次右移跳到“专家”。当前修正版统一使用 `9x9 / 10` 等 ASCII 文案，并通过有符号时间差阻止同轮重复输入，新增回绕回归断言。

结果页原“同盘”会让玩家在已知雷位下重玩，既不符合正式成绩公平性，中文语义也不自然。该能力和引擎入口已删除，结果页收敛为“再来一局”和“难度”两项；Fusion 字库已重新生成并包含新增文字。针对专家盘的第二轮反馈又将四角光标改为整格高对比脉冲框，输入改为独立 X/Y 八方向采样并缩短长按重复间隔。

用户再次实机体验后仍感到卡顿，且指出摇杆任意斜推都近似固定 45 度。原因有两层：`AppManager` 每轮调用 `onUpdateView()`，而扫雷此前在该回调中无条件让整个 320×218 surface 失效；即使仅移动一个光标格，`drawBoard()` 也会遍历并提交专家盘全部 480 格的绘制原语。输入侧则把越过死区的每个摇杆轴压缩为 `-1/0/+1`，丢掉了原始幅度。

当前修正取消了无条件全屏失效。光标移动只失效离开格和进入格，计时器、光标脉冲和标题火花各自失效最小区域；`drawBoard()` 以 LVGL 当前 clip 区域筛选格子。仅翻格波纹、旗帜生长和胜负演出才在短时间内全盘刷新。摇杆改为保留 `-512..512` 幅度，D-pad 覆盖为满幅输入；两个轴独立累积时间和幅度，在同一时间片内可产生不同跨格次数，方向改变时清空该轴残余量。修正完成 45 项全量测试、目标板构建和九态预览检查，尚未再次烧录。

2026-07-24 用户烧录局部重绘版本后反馈：专家盘中偶尔在已翻数字上按 A 没有立刻 chord，需要再按一次。输入链路的正常主路径仍是 BLE `ButtonDown` → `InputRouter` → `Activate`，但 App 现在同时采样手柄当前按钮状态：当检测到 A 上升沿且本轮没有收到对应命令时补发一次，收到正常命令时则用 25ms 窗口去重；首次进入扫雷会先同步当前按键，避免进入页面的同一次 A 顺便开局。成功 chord 的首格延迟由 42ms 改为近乎立即，普通翻格的首格等待缩短为 12ms，后续格仍按 14ms 曼哈顿距离展开。修正完成 45 项全量测试、目标板构建和九态预览检查，尚未烧录。

同日新增双击辅助：A 的第一下保持即时翻格/chord，260ms 内的第二下只展开当前可见信息已证明安全的格子；X 的第一下保持即时插/拔旗，第二下会先在第一下的原坐标恢复原旗帜状态，再执行自动插旗，所以双击不会把用户刚刚随手插下的旗当作证明。辅助推理只接收可见快照，先固定本轮候选，再统一执行，不会因新翻出的数字自动继续下一轮；旗帜不被当作数学事实，故错误旗帜不能令自动 A 踩雷，也不会由隐藏雷图静默修正。原生测试新增局部确定雷/安全、集合包含、安全/雷差集、歧义不动作、矛盾旗帜和错误旗帜保护，以及固定候选辅助动作覆盖；App 为 A/X 都增加与 BLE 事件相同的上升沿兜底。成功辅助在 HUD 中给出短时计数和短音/震动/RGB 反馈，提示区局部失效而不影响高密度棋盘正常帧率。

用户随后执行 `pio run -e playground -t upload --upload-port COM3` 并成功写入、校验和复位设备；但该命令与另一条正在运行的 `pio run` 共用 `.pio/build`，上传日志报告 Flash 2,398,721 bytes，而串行完成的最终构建为 2,397,165 bytes。为避免把并发增量产物当作验收基线，本次上传只记录为链路成功，双击辅助的真机结论应以提交后重新单独烧录的镜像为准。
